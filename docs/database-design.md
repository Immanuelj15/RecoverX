# RecoverX Database Architecture & Design Specification

> **Razorpay Buildathon 2026 Submission** | Track 03 — AI Revenue Recovery  
> *"Payments are facts. Recovery Cases are workflows. ML predicts. AI recommends. Policy controls. Actions execute. Outcomes measure. Audit logs explain."*

---

## 1. Conceptual Architecture & Data Flow

RecoverX uses MongoDB as its primary operational database, structured around an enterprise fintech conceptual architecture:

```
MERCHANT
   │
   ├── CUSTOMERS
   │
   └── PAYMENTS (Source of Truth for Financial Event)
             │
             ▼
       RECOVERY_CASE (Workflow Lifecycle Engine)
             │
       ┌─────┴─────────────┬─────────────────┐
       ▼                   ▼                 ▼
ML_PREDICTION        AI_DECISION      POLICY_DECISION
(Probabilities)     (Strategies)       (Guardrails)
                           │                 │
                           └────────┬────────┘
                                    ▼
                             RECOVERY_ACTION (Attempted Execution)
                                    │
                                    ▼
                             RECOVERY_OUTCOME (Measured Money Recovered)

IMPORTANT EVENTS ───────► AUDIT_LOG (Immutable Append-Only Audit Trail)
RAZORPAY WEBHOOKS ──────► WEBHOOK_EVENT (Idempotent Event Ingestion)
```

---

## 2. Core Collections & Responsibilities

| Collection | Model Name | Primary Responsibility |
| :--- | :--- | :--- |
| `merchants` | `Merchant` | Merchant account settings, currency, environment (`test`/`production`), financial guardrails. |
| `customers` | `Customer` | Customer profile, aggregate payment stats, LTV in paise. |
| `payments` | `Payment` | Immutable financial facts of raw payment attempts & failure reasons. |
| `recovery_cases` | `RecoveryCase` | Active or closed recovery workflow state machine tracking revenue at risk. |
| `ml_predictions` | `MLPrediction` | Immutable ML model predictions (`probability`, `risk_band`). No target leakage. |
| `ai_decisions` | `AIDecision` | Recommended recovery interventions generated by AI LLM agent or heuristic fallbacks. |
| `policy_decisions` | `PolicyDecision` | Guardrail evaluations enforcing max retries, high value limits, allowed actions. |
| `recovery_actions` | `RecoveryAction` | Bounded execution attempts with unique `idempotency_key` enforcement. |
| `recovery_outcomes` | `RecoveryOutcome` | Source-of-truth for actual recovered revenue (`amount_recovered_paise`). |
| `audit_logs` | `AuditLog` | Append-only compliance log tracing events with `correlation_id`. |
| `webhook_events` | `WebhookEvent` | Webhook ingestion log enforcing unique `{ merchant_id, event_id }`. |

## 3. Money Representation Rule (Integer Paise)

To avoid floating-point rounding errors in financial transactions:
- All financial values (`amount_paise`, `revenue_at_risk_paise`, `amount_recovered_paise`, `customer_ltv_paise`, `high_value_threshold_paise`) are stored as **non-negative integers in paise** (1 INR = 100 Paise).
- Example: **₹8,499.50** is stored as **`849950`**.
- Division by 100 occurs strictly during frontend display.

---

## 4. Multi-Tenancy & Scoping

- Every business collection includes a required `merchant_id` field referencing the `Merchant` collection.
- All database queries and repository operations scope queries by `merchant_id`:
  ```js
  paymentRepository.findByPaymentId(merchantId, paymentId)
  ```
- Cross-merchant data leakage is strictly prevented.

---

## 5. Centralized State Machine Transitions

State transitions for `RecoveryCase` are managed strictly by a centralized state machine utility (`stateMachine.js`). Direct controller mutations are forbidden.

```
DETECTED ──► ANALYZING ──► PREDICTED ──► RECOMMENDED ──► POLICY_CHECK
                                                              │
                    ┌─────────────────────────────────────────┼────────────────────────────────────────┐
                    ▼                                         ▼                                        ▼
             ACTION_APPROVED                          ESCALATED (Human Approval)              STOPPED (Policy Block)
                    │
                    ▼
            ACTION_EXECUTING
                    │
       ┌────────────┴────────────┐
       ▼                         ▼
RECOVERY_SUCCESS          RECOVERY_FAILED ──► POLICY_CHECK / ESCALATED
```

## 6. Indexing & Idempotency Strategy

- `merchants`: `{ merchant_code: 1 }` (UNIQUE)
- `customers`: `{ merchant_id: 1, customer_id: 1 }` (UNIQUE), `{ merchant_id: 1, created_at: -1 }`
- `payments`: `{ merchant_id: 1, payment_id: 1 }` (UNIQUE), `{ merchant_id: 1, status: 1, created_at: -1 }`
- `recovery_cases`: `{ merchant_id: 1, case_id: 1 }` (UNIQUE), `{ merchant_id: 1, status: 1, created_at: -1 }`
- `recovery_actions`: `{ idempotency_key: 1 }` (UNIQUE)
- `webhook_events`: `{ merchant_id: 1, event_id: 1 }` (UNIQUE)
- `audit_logs`: `{ recovery_case_id: 1, timestamp: -1 }`, `{ correlation_id: 1, timestamp: -1 }`

---

## 7. Soft Delete & Data Retention

- Financial and audit records (`payments`, `recovery_outcomes`, `audit_logs`, `webhook_events`) are **never soft-deleted**.
- Status indicators (`status: "active" | "inactive"`) are used for configuration entities (`merchants`, `customers`).
